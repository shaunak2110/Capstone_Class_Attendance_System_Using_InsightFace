# Requirements Document

## Introduction

This feature prepares the existing attendance system for cloud deployment. The backend (FastAPI + InsightFace) will be hosted on Render, the frontend (React + Vite) on Vercel, and the database migrated from a local SQL Server Express instance (Windows Authentication) to Azure SQL Database (SQL authentication). The goal is to make the system fully accessible from any laptop or mobile browser over the internet, while preserving all existing functionality: face recognition, image uploads, attendance CSV generation, and role-based access control.

## Glossary

- **Backend**: The FastAPI Python application located in `backend/`.
- **Frontend**: The React + Vite application located in `frontend/`.
- **Render**: Cloud platform-as-a-service used to host the Backend as a native Python web service.
- **Vercel**: Cloud platform used to host the Frontend as a static site.
- **Azure_SQL**: Microsoft Azure SQL Database, the cloud-hosted relational database replacing the local SQL Server Express instance.
- **ODBC_Driver**: The ODBC driver used by `pyodbc` to connect to SQL Server; must be available in the Render runtime environment.
- **InsightFace_Models**: The `buffalo_l/` directory containing five ONNX model files (`det_10g.onnx`, `w600k_r50.onnx`, `1k3d68.onnx`, `2d106det.onnx`, `genderage.onnx`) required by the InsightFace engine.
- **Procfile**: A Render/Heroku-style process file that declares the command used to start the Backend web process.
- **runtime.txt**: A file that declares the Python version for Render's native Python environment.
- **CORS**: Cross-Origin Resource Sharing middleware in the Backend that controls which origins may call the API.
- **VITE_API_URL**: The environment variable read by the Frontend at build time to set the base URL for all API calls.
- **PORT**: The environment variable injected by Render at runtime specifying the TCP port the Backend must listen on.
- **DB_CONNECTION_STRING**: A single environment variable holding the full `pyodbc`-compatible connection string for Azure SQL, replacing the separate `SERVER` and `DATABASE` variables and the `Trusted_Connection=yes` clause.
- **SECRET_KEY**: An environment variable holding the application secret used for any token signing or session security.
- **ALLOWED_ORIGINS**: An environment variable holding a comma-separated list of permitted CORS origins for the Backend.
- **Attendance_CSV**: A CSV file generated by the Backend and returned to the client via the `/user/download-csv/{lec_id}` endpoint.
- **Schedule_Template**: A recurring lecture schedule stored in the database and used to auto-generate `Lecture_Master` rows.

## Requirements

### Requirement 1: Backend Port Configuration

**User Story:** As a DevOps engineer, I want the Backend to read its listening port from the `PORT` environment variable, so that Render can dynamically assign the port at runtime without requiring code changes.

#### Acceptance Criteria

1. WHEN the `PORT` environment variable is set, THE Backend SHALL bind the HTTP server to the port specified by `PORT`.
2. WHEN the `PORT` environment variable is not set, THE Backend SHALL bind the HTTP server to port `8000` as the default.
3. THE Backend SHALL always bind to host `0.0.0.0` so that it is reachable from outside the container.

---

### Requirement 2: Render Deployment Files

**User Story:** As a DevOps engineer, I want standard Render deployment files present in the repository, so that Render can automatically detect the runtime and start command without manual dashboard configuration.

#### Acceptance Criteria

1. THE Backend SHALL include a `Procfile` at `backend/Procfile` containing a `web` process entry that starts the FastAPI application using `uvicorn` with the `PORT` environment variable.
2. THE Backend SHALL include a `runtime.txt` at `backend/runtime.txt` declaring the Python version compatible with the project's dependencies.
3. WHEN Render reads `backend/Procfile`, THE Backend SHALL start successfully without additional manual configuration of the start command.

---

### Requirement 3: Database Connection — SQL Authentication

**User Story:** As a DevOps engineer, I want the Backend to connect to Azure SQL Database using SQL username/password authentication, so that the system works in cloud environments where Windows Authentication is unavailable.

#### Acceptance Criteria

1. THE Database_Module SHALL read the database connection from the `DB_CONNECTION_STRING` environment variable when it is set.
2. WHEN `DB_CONNECTION_STRING` is set, THE Database_Module SHALL use it directly as the `pyodbc` connection string, replacing the `Trusted_Connection=yes` Windows Authentication string.
3. WHEN `DB_CONNECTION_STRING` is not set, THE Database_Module SHALL fall back to constructing a connection string from the `SERVER` and `DATABASE` environment variables using `Trusted_Connection=yes` for local development compatibility.
4. THE Database_Module SHALL validate that a connection can be established at startup and SHALL raise a descriptive error if the connection fails.
5. THE `DB_CONNECTION_STRING` for Azure SQL SHALL include `Encrypt=yes;TrustServerCertificate=no;Connection Timeout=30` to satisfy Azure SQL's TLS requirements.

---

### Requirement 4: CORS Restriction for Production

**User Story:** As a security engineer, I want the Backend CORS policy to be restricted to the deployed Vercel domain in production, so that arbitrary origins cannot call the API.

#### Acceptance Criteria

1. THE Backend SHALL read the list of allowed CORS origins from the `ALLOWED_ORIGINS` environment variable.
2. WHEN `ALLOWED_ORIGINS` is set, THE Backend SHALL configure the `CORSMiddleware` to allow only the origins listed in `ALLOWED_ORIGINS` (comma-separated).
3. WHEN `ALLOWED_ORIGINS` is not set, THE Backend SHALL fall back to allowing all origins (`*`) to preserve local development behaviour.
4. THE Backend SHALL continue to allow all HTTP methods and headers for allowed origins.
5. THE Backend SHALL allow credentials (`allow_credentials=True`) for allowed origins.

---

### Requirement 5: Frontend Production Build Configuration

**User Story:** As a frontend developer, I want the Vercel-deployed Frontend to point to the Render backend URL, so that all API calls reach the correct server in production.

#### Acceptance Criteria

1. THE Frontend SHALL read the backend base URL from the `VITE_API_URL` environment variable at build time.
2. WHEN `VITE_API_URL` is set to a non-empty string, THE Frontend SHALL use that value as the `baseURL` for all `axios` requests.
3. WHEN `VITE_API_URL` is empty or not set, THE Frontend SHALL use an empty string as the `baseURL`, relying on the Vite dev proxy for local development.
4. THE Frontend SHALL include a `vercel.json` configuration file that rewrites all non-asset routes to `index.html` to support client-side routing.
5. THE Frontend build output SHALL be placed in the `frontend/dist` directory, which Vercel SHALL serve as the static site root.

---

### Requirement 6: InsightFace Model Availability on Render

**User Story:** As a system administrator, I want the InsightFace ONNX models to be available on Render at the expected path, so that face recognition works correctly after deployment.

#### Acceptance Criteria

1. THE InsightFace_Models directory (`buffalo_l/`) SHALL be committed to the repository and included in the Render deployment so that the models are available at runtime without a separate download step.
2. THE Backend SHALL configure InsightFace to load models from a path resolvable relative to the application root, using an environment variable `MODEL_ROOT` when set, defaulting to the `buffalo_l/` directory at the workspace root.
3. WHEN the InsightFace engine initialises, THE Backend SHALL log the resolved model path so that deployment issues can be diagnosed from Render logs.
4. IF the model directory does not exist at the resolved path, THEN THE Backend SHALL raise a descriptive startup error identifying the missing path.

---

### Requirement 7: Image Upload Compatibility

**User Story:** As a teacher, I want image uploads for face recognition and student enrollment to work correctly when the Frontend is on Vercel and the Backend is on Render, so that attendance marking and student enrollment are not broken by the cloud deployment.

#### Acceptance Criteria

1. THE Backend SHALL accept multipart/form-data and JSON payloads containing base64-encoded images on all existing image upload endpoints.
2. WHEN the Frontend sends a request to an image upload endpoint, THE Backend SHALL process the request regardless of whether the Frontend origin is `localhost` or the Vercel production domain, provided the origin is in `ALLOWED_ORIGINS`.
3. THE Backend SHALL enforce a maximum request body size sufficient to handle batch image uploads (at least 50 MB) and SHALL return HTTP 413 with a descriptive message if the limit is exceeded.

---

### Requirement 8: Attendance CSV Generation

**User Story:** As a teacher, I want to download attendance CSV files from the cloud-deployed system, so that I can export attendance records after marking.

#### Acceptance Criteria

1. WHEN the `/user/download-csv/{lec_id}` endpoint is called, THE Backend SHALL generate the CSV file in a writable temporary directory available on Render (e.g., `/tmp`).
2. THE Backend SHALL return the CSV file as a streaming response with `Content-Disposition: attachment` so that the browser triggers a file download.
3. IF the CSV file cannot be written to the temporary directory, THEN THE Backend SHALL return HTTP 500 with a descriptive error message.

---

### Requirement 9: Azure SQL Schema Migration

**User Story:** As a database administrator, I want a migration script that creates the AttendanceDB schema on Azure SQL Database, so that the cloud database is ready for use without manual table creation.

#### Acceptance Criteria

1. THE Migration_Script SHALL create all required tables (`Login_Master`, `User_Master`, `Student_Master`, `Student_Embeddings`, `Lecture_Master`, `Request_Master`, `Attendance_Record`) on Azure SQL Database.
2. THE Migration_Script SHALL NOT include `USE master` or `CREATE DATABASE` statements, as Azure SQL does not support these commands in the same way as SQL Server Express.
3. THE Migration_Script SHALL NOT include `Trusted_Connection` or Windows Authentication references.
4. THE Migration_Script SHALL be idempotent: re-running it on a database that already has the schema SHALL NOT produce errors (using `IF NOT EXISTS` guards or equivalent).
5. THE Migration_Script SHALL preserve all foreign key constraints, unique constraints, check constraints, and indexes from the original schema.

---

### Requirement 10: Environment Variable Documentation

**User Story:** As a developer, I want a deployment guide with all required environment variables and step-by-step instructions, so that I can deploy the system to Vercel, Render, and Azure SQL without guessing configuration values.

#### Acceptance Criteria

1. THE Deployment_Guide SHALL be a Markdown file at `deployment.md` in the repository root.
2. THE Deployment_Guide SHALL document all required and optional environment variables for the Backend, including `DB_CONNECTION_STRING`, `ALLOWED_ORIGINS`, `PORT`, `MODEL_ROOT`, and `SECRET_KEY`, with example values.
3. THE Deployment_Guide SHALL document the required environment variable for the Frontend: `VITE_API_URL`, with an example value pointing to the Render backend URL.
4. THE Deployment_Guide SHALL include step-by-step instructions for deploying the Frontend to Vercel.
5. THE Deployment_Guide SHALL include step-by-step instructions for deploying the Backend to Render.
6. THE Deployment_Guide SHALL include step-by-step instructions for setting up Azure SQL Database and running the migration script.
7. THE Deployment_Guide SHALL include a section on local development setup that explains how to run the system without cloud services.

---

### Requirement 11: Schedules Table Migration

**User Story:** As a database administrator, I want the `Schedules` table (used for recurring lecture templates) included in the Azure SQL migration script, so that the schedule feature works after cloud deployment.

#### Acceptance Criteria

1. THE Migration_Script SHALL include the `Schedules` table definition with all columns, constraints, and indexes present in the local SQL Server Express schema.
2. THE Migration_Script SHALL preserve the foreign key relationship between `Schedules` and `Login_Master`.
